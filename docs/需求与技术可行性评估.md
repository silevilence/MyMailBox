# MyMailBox 需求与技术可行性评估

评估日期：2026 年 11 月 16 日。状态：已确认全 JIT、框架依赖发布、优先复用 CordiSharp；功能设计仍为评估，尚未开始实现或执行兼容性 PoC。

目标是 Windows x64 多邮箱客户端，覆盖接入、收发、离线存储、迁移、搜索和自动化，并把产品能力通过内置或外部插件提供。当前仓库处于需求和规范整理阶段，本评估不假定已有应用实现。

用户已确认：**全部使用常规 .NET JIT，框架依赖发布，由用户安装系统 .NET 10，插件系统优先复用 CordiSharp。** 本文保留 NativeAOT 对比作为决策依据，不再把它作为待实施方案或安排双路线 PoC。

全 JIT 更贴合 C# 插件、运行时扩展、内置能力可替换、完善 UI 和 Outlook 兼容的目标。邮件数量增加时的交互流畅度，通过数据分页、索引、后台调度和 UI 虚拟化保证。发布流程已确定为 generate-changelog 生成记录并同步版本、提交、打 Tag、推送，随后由 GitHub Actions 自动构建 NSIS 安装包并发布 Release；执行规范写入根目录 `AGENTS.md`。

## 一 技术路线比较

### 1 全 JIT 与全 NativeAOT

| 比较项 | 全 JIT 框架依赖发布 | 全 NativeAOT |
| --- | --- | --- |
| 主程序 | Avalonia、C#、.NET 10，`win-x64` | 相同技术栈，发布时编译为本机代码 |
| 系统依赖 | 用户安装匹配架构的 .NET 10 Runtime；通常无需 SDK | 自研程序不需要系统 .NET Runtime；仍可能依赖 WebView2、SQLite 等原生组件 |
| 外部 C# 插件 | 可加载普通托管 DLL，复用 NuGet 和现有 .NET 工具链 | 不能在主程序加载发布后新增的托管 DLL |
| CordiSharp | 可优先直接复用，仍需生命周期和 UI 集成验证 | 完整加载器不可直接用；尝试静态子集，必要时改造或实现子集 |
| 外部 Avalonia UI | 可提供托管控件，但需要统一框架版本和严格释放约定 | 默认声明式 UI；不能经 C ABI、WASM 或 IPC 传递任意托管 `Control` |
| 热卸载 | collectible AssemblyLoadContext 协作卸载，存在引用残留风险 | 原生 C/C++ DLL、WASM 实例、独立进程分别有不同卸载机制；C# NativeAOT DLL 不支持卸载 |
| 兼容现有库 | 最宽，适合 Outlook、MIME、富文本和插件生态 | 每个依赖都需验证裁剪、反射、序列化和原生互操作 |
| 启动与占用 | 首次 JIT 等成本需测量，可后续评估 ReadyToRun | 通常有启动收益；实际总占用仍受浏览器、索引和缓存影响 |
| 安装包 | 不包含 .NET Runtime，但仍包含应用及其依赖 | 包含必要运行时代码；不能预先断言一定比框架依赖包小 |
| 运维 | 系统运行时升级由用户或组织管理，应用控制兼容版本范围 | .NET 运行时代码的更新随应用重新发布；插件与宿主分别管理版本 |
| 开发复杂度 | 较低，风险集中于卸载和邮件业务 | 较高，还要实现跨边界 SDK、序列化、调试和 UI 协议 |

微软明确支持框架依赖发布与 apphost EXE；不需要把“用户安装 .NET”理解为必须使用命令行启动。Avalonia 官方支持 NativeAOT。NativeAOT 不支持动态托管程序集加载和运行时代码生成；并不是所有反射都禁止，但反射目标必须能在构建时分析和保留。[.NET 发布方式](https://learn.microsoft.com/en-us/dotnet/core/deploying/)、[Avalonia NativeAOT](https://docs.avaloniaui.net/docs/deployment/native-aot)、[NativeAOT 限制](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)

WPF 仍不适合作为保持 NativeAOT 前提下的替代：微软当前将 WPF 列为不支持 trimming 的框架。若选 JIT，WPF 才成为一般意义上的可选 UI 框架；没有必要因此放弃用户指定的 Avalonia。[微软 trimming 不兼容项](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/incompatibilities)

已确定的发布参数如下，不表示已经构建：

```powershell
dotnet publish -c Release -r win-x64 --self-contained false -p:PublishAot=false -p:PublishTrimmed=false
```

默认采用 .NET 10 的兼容补丁更新策略，不默默跨主版本运行。运行时要求由最终 `runtimeconfig.json` 决定：普通 Avalonia 应用通常依赖 `Microsoft.NETCore.App`；若某兼容组件引入 Windows Desktop Framework，再明确其额外需求。NSIS 检查 x64 运行时并提供缺失说明和官方安装入口，不把运行时打入应用包，也不未经用户操作自动安装。SDK 和 x86 Runtime 不能作为 x64 运行依赖检查的替代。[运行时选择](https://learn.microsoft.com/en-us/dotnet/core/versions/selection)

### 2 全 AOT 的插件候选不能混为一谈

| 机制 | 能力和适合场景 | 必须接受的限制 |
| --- | --- | --- |
| C/C++ 或 Rust 提供 C ABI DLL | 原生库接入、高性能解析、可信插件 | 稳定 ABI、内存所有权、调用约定、回调和线程退出必须严格定义；同进程崩溃影响主程序 |
| C# NativeAOT DLL 暴露 C ABI | 可从 C# 生成原生入口，适合启动后固定的核心插件 | 官方不支持卸载该类库；不能用 `FreeLibrary` 兑现普通插件的真正热卸载 |
| WASM 默认即时编译 | 动态载入 `.wasm`，有沙箱与宿主能力边界 | Wasmtime 等默认编译路径会生成机器码；没有 CLR 不等于完全没有 JIT |
| WASM 解释执行 | 无机器码 JIT，适合自定义条件、文本处理和轻量动作 | 仍需分发解释器；不是“所有插件都预编译为机器码”，性能及 .NET guest 工具链需单独验证 |
| WASM 预编译 | 发布阶段生成目标平台产物，客户端运行时不再编译 | 产物绑定引擎版本、目标及配置；不能把任意第三方预编译文件当作安全 Wasm 字节码 |
| 独立 NativeAOT EXE + IPC | C# 邮箱提供者、导入器、复杂插件；进程退出可可靠释放代码 | 需要协议、DTO、超时、取消、流式传输；UI 用声明贡献或独立窗口；有进程开销 |

微软明确指出 NativeAOT 共享库不支持卸载。Wasmtime 官方提供预编译和 Pulley 解释器路线；具体 C# 绑定、Windows 发布配置及禁用运行时编译的完整链路仍须验证。[NativeAOT 原生库](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/libraries)、[Wasmtime 预编译](https://docs.wasmtime.dev/examples-pre-compiling-wasm.html)、[Pulley 解释器](https://docs.wasmtime.dev/examples-pulley.html)

严格无运行时编译的 Wasmtime 部署应在构建端预编译，并在客户端禁用 Cranelift/Winch 编译器；Pulley 路线也可提前生成其字节码。Windows x64 与 C API 在官方支持范围内，但这不等于选定的 .NET 包已通过 NativeAOT。预编译模块反序列化只做有限校验，必须使用可信构建产物；不能因为扩展名是 `.cwasm` 就认为它与受校验的原始 WASM 具有相同信任前提。[Wasmtime 支持等级](https://docs.wasmtime.dev/stability-tiers.html)、[预编译模块加载限制](https://docs.wasmtime.dev/api/wasmtime/struct.Module.html#method.deserialize)

原生 C ABI 应使用版本化结构体、UTF-8 字节串和不透明句柄，明确由哪一方分配和释放内存，以错误码替代跨边界异常。提供 create/start/stop/destroy 等生命周期入口，卸载前等待线程、回调和在途调用退出；Windows 的 `FreeLibrary` 本身不会替插件完成这些工作。[Windows FreeLibrary](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-freelibrary)

如果最终选择全 AOT，建议以“**静态内置插件 + 外部 AOT 进程插件**”为通用扩展机制；C ABI 用于必要原生集成，WASM 作为条件、转换器等受限扩展的第二阶段能力。不要首版同时开发三套通用插件 SDK。WASM 适合纯计算扩展，但邮件网络协议、OAuth、证书、文件访问与 UI 都要额外设计宿主接口，它不会自动消除这些成本。

这里的全 AOT 指自研 .NET 主程序和可执行插件不依赖 CoreCLR JIT。若进一步要求 WebView、WASM 等所有组件也绝无运行时代码编译，需要把这个要求单列为验收项；WASM 解释执行与严格的“所有插件均提前编译”也应分别命名。

## 二 插件模型与 CordiSharp

### 1 三个分类维度

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| 生命周期 | 核心、普通 | 是否允许本次运行中更换或撤销 |
| 分发来源 | 内置、外部 | 随应用提供，还是用户后装 |
| 执行载体 | 静态代码、托管加载上下文、原生模块、WASM、独立进程 | 取决于最终技术路线 |

内置不等于核心，外部也不等于普通。只有改变后会破坏当前运行环境或数据一致性的能力才默认归为核心。已编译到 AOT 主程序的普通插件可逻辑停用和释放实例，但机器码随程序存在；替换该内置代码需要应用更新。若要求内置普通插件也能独立更换二进制，应从一开始把它作为独立模块或进程分发。

最小宿主只保留启动入口、契约、加载与恢复机制；邮箱、规则、搜索、编辑器、选择器等产品能力都由插件提供。宿主不能通过“大量特殊分支”绕过自家插件接口。插件测试应证明某项内置能力可以被另一实现替换，而不只证明它有一个接口。

### 2 CordiSharp 评估顺序

本次定位到 `oniemiddle/CordiSharp`，核查提交 `01f121728be1455101e260d69ffcc27c8599e3fa`，目标框架为 .NET 10。源码有 Source Generator，但动态加载仍依赖 collectible AssemblyLoadContext；构造器、注入及元数据注册仍存在反射路径。因此不能由“有源生成器”推断完整 AOT 兼容。

- JIT 路线：优先复用 CordiSharp，通过项目适配层约束插件接口和生命周期，不先另写框架。
- AOT 路线：先验证显式注册、强类型工厂的静态子集；排除运行时程序集扫描和动态加载；若裁剪仍影响核心路径，再评估修改源码。
- 只有改造成本明显高于收益时，才实现所需的 Cordis 子集，避免另造完整平台。

证据：[项目配置](https://github.com/oniemiddle/CordiSharp/blob/01f121728be1455101e260d69ffcc27c8599e3fa/src/CordiSharp/CordiSharp.csproj)、[程序集加载器](https://github.com/oniemiddle/CordiSharp/blob/01f121728be1455101e260d69ffcc27c8599e3fa/src/CordiSharp/Loading/AssemblyLoaderService.cs)、[插件加载器](https://github.com/oniemiddle/CordiSharp/blob/01f121728be1455101e260d69ffcc27c8599e3fa/src/CordiSharp/Registry/PluginLoader.cs)、[元数据注册](https://github.com/oniemiddle/CordiSharp/blob/01f121728be1455101e260d69ffcc27c8599e3fa/src/CordiSharp/Registry/PluginMetadataRegistry.cs)。

必要子集包括 Context/Scope、明确服务键与版本、依赖声明、拓扑激活、异步启停、可撤销注册、事件订阅清理、配置验证、错误隔离和依赖级联停用。Cordis 官方当前引导至 DeepSeek Harness primer；本项目借鉴其生命周期思想，双配置语义按本需求单独定义，不声称与上游实现完全一致。[Cordis 官方仓库](https://github.com/cordiverse/cordis)、[Cordis primer](https://deepseek-harness.github.io/deepseek-harness/reference/cordis-primer)

CordiSharp 的现有 HotSwap 路径在预检查后会停止旧实例，再加载新实例；不能把该 API 当成自动回滚的无损事务。项目适配层仍需补充操作排空、状态迁移、失败恢复和 UI 注册撤销。DeepSeek Harness 当前采用 profile、bundle 与 patch 分层，热重载由相应插件和 profile 控制；本需求的双文件划分是本项目规则。[CordiSharp 热替换源码](https://github.com/oniemiddle/CordiSharp/blob/01f121728be1455101e260d69ffcc27c8599e3fa/src/CordiSharp/Loading/AssemblyLoaderService.cs)、[Harness 架构](https://deepseek-harness.github.io/deepseek-harness/en/reference/)

### 3 核心与普通插件的建议边界

| 核心插件候选 | 普通插件候选 |
| --- | --- |
| 当前工作空间的数据引擎、事务与迁移服务 | QQ、163、IMAP、POP3、Graph、Exchange、本地邮箱适配器 |
| 身份、密钥与权限基础实现 | 导入器、导出器、内容抽取器、搜索扩展 |
| 宿主 UI 框架、基础调度和命令执行协议 | 邮箱/目录选择器、规则编辑器、阅读器、编辑器、通知 |
| 查询与动作协议的基础执行语义 | 调度提供者、触发器、条件、动作、模板 |

这是默认分组，最终以能否安全撤销为准。例如底层 SQLite 工作空间不能在读写时直接替换，但挂在其上的本地邮箱提供者可以在停止使用后卸载。阅读器可以替换，但必须先关闭对应视图；编辑器须先保存草稿。核心插件的内部依赖不能要求一个可随意卸载的普通插件永久在线。

### 4 两份配置与持久状态

- `profiles/<profile-id>/core.json`：核心插件清单、绑定和配置；仅启动读取；GUI 提供默认 Profile；高级用户可修改，下次启动生效。
- `profiles/<profile-id>/plugins.json`：普通插件实例、启用状态、配置及绑定；监听变化并热重载。
- 邮件、账户、规则、任务和运行日志属于业务数据，不硬塞进上述两个插件配置文件；密码和 token 存在凭据存储中，配置只保留引用。

配置须有 schemaVersion、插件与实例稳定 ID、SDK 兼容范围、依赖和权限清单。重载流程为读取完整快照、验证、计算差异、准备新实例、停止旧实例接单、排空在途操作、切换注册、清理旧实例。无效配置保留上次可用版本，并显示具体字段错误。

配置回退只能恢复配置和服务绑定，不能假定已发送邮件、已删除远端邮件等外部副作用能被回滚。单实例禁用、配置更新、插件版本更换、整个依赖组停用需要不同策略。插件文件使用版本目录，避免覆盖正在使用的 DLL。

### 5 热卸载的产品承诺

JIT 的 `AssemblyLoadContext.Unload()` 只是发起协作卸载。未退出的线程、静态引用、事件、定时器、委托、UI 模板和宿主缓存都可能阻止回收。SDK 必须提供统一释放登记，主程序避免把插件私有类型存入全局缓存。契约程序集由默认上下文共享，插件私有依赖由自己的加载上下文解析。[微软卸载说明](https://learn.microsoft.com/en-us/dotnet/standard/assembly/unloadability)、[官方插件教程](https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support)

普通插件应承诺“符合 SDK 生命周期规范的实现能够在不退出应用的情况下停用、更新和重新启用”，并以循环卸载验证。失控插件不保证可在同进程强制卸载；需要强隔离的插件可使用与主程序相同运行路线的独立进程。JIT 加载上下文、C ABI DLL 和普通独立进程都不自动构成安全沙箱。

Avalonia 官方问题记录包含复杂控件动画、Observable 及资源解析造成程序集残留的案例；它不能证明所有版本和控件都失败，但足以要求实际验收。即使 JIT 方案也建议普通插件优先贡献宿主渲染的表单、命令、菜单、列表列和选择器；任意自定义 Avalonia 控件作为有单独兼容规范的高级扩展。[Avalonia 插件卸载问题](https://github.com/AvaloniaUI/Avalonia/issues/17129)

插件移除时，引用其条件或动作的规则应显示“缺少插件，暂停执行”，不能把缺失条件视作 false 后经 NOT 变成 true，也不能静默跳过动作。

### 6 应公开的扩展契约

下表是职责划分，不是最终 C# API 签名。每个契约都应提供版本协商、取消、错误分类、能力探测和测试夹具；内置实现使用同一契约。

| 扩展领域 | 应暴露的能力 |
| --- | --- |
| 账户与身份 | 账户类型描述、配置 schema、发现与验证、授权/续期、发送身份、共享邮箱与权限 |
| 邮箱协议 | 目录枚举、增量同步、原文和附件流、发送、上传、移动/复制、标记、配额、远端搜索 |
| 本地数据 | 工作空间引擎、本地邮箱格式、事务/备份/恢复、版本迁移、完整性检测；稳定运行绑定可为核心插件 |
| 导入 | 源探测、账户配置发现、项目枚举、字段映射、能力/损失报告、进度、断点、去重 |
| 导出 | 格式描述、选项 schema、批处理流、内容和元数据保真说明、恢复/验证能力 |
| 搜索 | 字段、运算符、语法扩展、查询规划、索引后端、分词、附件文本抽取、结果与高亮 |
| 自动化 | 触发器、调度器、任务前置条件、邮件谓词、动作、预览、幂等键、补偿及执行报告 |
| 阅读与编辑 | MIME/特殊内容处理、阅读器、编辑器、签名模板、附件预览、地址建议、邮件安全策略 |
| UI | 邮箱/目录/身份选择器、条件编辑器、设置页、页面贡献、命令、菜单、列、快捷键、主题与本地化 |
| 系统服务 | 通知、凭据存储、更新源、诊断、代理、备份目标、后台任务；权限由宿主统一执行 |

宿主保留身份、权限及数据访问入口，不向所有插件默认暴露整个数据库或所有 token。权限可按账户、邮件内容、发送/删除、文件目录和网络访问细分；同进程可信插件权限主要是契约和审核约束，不应宣称可抵御恶意代码。跨进程/WASM 扩展通过代理能力访问，并配合适用的 OS 或运行时限制。

## 三 邮箱接入与账户模型

### 1 接入矩阵

| 类型 | 建议接入 | 特别边界 |
| --- | --- | --- |
| QQ 邮箱 | IMAP + SMTP，POP3 可选；厂商预设插件复用协议插件 | 启用服务、授权码、连接限制、特殊文件夹映射 |
| 163 邮箱 | IMAP + SMTP，POP3 可选；厂商预设 | 实测授权、客户端识别及厂商限制，错误提示需可操作 |
| Outlook.com 个人邮箱 | OAuth + Microsoft Graph 优先；协议接入作为经验证的另一实现 | 个人账号权限、增量同步、附件、发送及授权失效 |
| Microsoft 365 / Exchange Online | OAuth + Graph | 租户同意、条件访问、共享邮箱和限流；不能把管理员限制当作客户端 bug |
| 本地/混合 Exchange | 先验证 EWS、认证及 Autodiscover；允许时 IMAP + SMTP 降级 | Graph 不是本地 Exchange 的通用替代；不能用网页版登录成功推断 EWS 可用 |
| 通用 IMAP | IMAP 接收/同步，可搭配独立 SMTP | TLS、OAuth/密码、证书、代理、UIDVALIDITY、IDLE、断线重连 |
| 通用 POP3 | POP3 拉取 + 本地状态，可搭配 SMTP | 不伪装成具有 IMAP 目录及完整双向同步；处理 UIDL、留存与删除策略 |
| 仅发送 | SMTP 或其他发送提供者 | UI 隐藏收件能力，规则不能选其作为接收来源 |
| 仅接收 | 接收提供者 | 发件账户选择器不列入；可另指定默认回复账户 |
| 本地邮箱 | 自定义本地格式提供者 | 默认存储/检索/接收归档，无网络发送；发送身份另行绑定 |

Graph 官方支持个人和组织 Outlook 云邮箱。Exchange Online 的 EWS 于 2026 年 10 月起分阶段停用，计划 2027 年 4 月完全停用；截至本评估日期，不能将其作为新的云邮箱长期基础。这不等于本地 Exchange Server 同步停用 EWS。[Graph 邮件 API](https://learn.microsoft.com/en-us/graph/api/resources/mail-api-overview?view=graph-rest-1.0)、[EWS 退役安排](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-ews-exchange-online)、[Exchange 官方说明](https://techcommunity.microsoft.com/blog/exchange/exchange-online-ews-your-time-is-almost-up/4492361)

用户提供的截图显示经典 Outlook、Microsoft Exchange 类型及公司自有域名的 `/owa/` 入口。它倾向于本地或混合部署，但不能确认版本、邮箱实际托管位置、EWS 开放情况、认证方式或管理员策略。**公司邮箱真实接入应成为第一阶段的通过条件。** 后续需通过授权测试或 IT 提供信息确认服务器版本、可用端点、VPN、认证与第三方客户端策略；本次没有访问公司服务器或读取凭据。

MailKit/MimeKit 可作为通用协议和 MIME 层候选。当前 MailKit 源码已包含 net10.0、AOT 兼容声明以及包级 AOT 探针，但不能据此认为所有依赖和本应用路径已经验证。应固定版本，验证 IMAP/POP3/SMTP、中文编码、TLS、OAuth、附件及需要的密码学模块。[MailKit 项目配置](https://github.com/jstedfast/MailKit/blob/master/MailKit/MailKit.csproj)、[MailKit 验证说明](https://github.com/jstedfast/MailKit#package-smoke-tests)

### 2 账户、身份和能力

每个账户保存：自动生成且不随名称变化的 UUID、可选唯一 alias、自定义显示名、providerId、tags、颜色、备注、排序、收发配置、凭据引用、同步策略和状态。自动化内部绑定 UUID；alias 供高级配置使用，修改时统一更新引用或保留映射。通常不允许在普通 GUI 修改 UUID；恢复/迁移时保留原 ID，冲突必须报告。

账户不等于邮件地址：一个账户可有多个发送身份、别名和委托身份。文件夹有稳定本地 ID 和特殊用途映射，不能以显示路径或英文 `Inbox` 为唯一定位。邮件有应用内稳定 ID 和远端映射；IMAP 映射包含账户、目录、UIDVALIDITY 和 UID，不能仅以 Message-ID 去重。

能力按账户及目录实际权限声明，例如 Read、Send、Append、MoveWithinStore、ImportPreservingMetadata、Flags、Quota、ServerSearch、SharedMailbox、Rules、Push。UI、动作引擎和插件都先检查能力；离线、权限撤销、配额未知与永久不支持需要分别表达。

## 四 导入 导出与本地存储

### 1 Outlook 账户配置导入是必做项

建议承诺：发现支持的经典 Outlook Profile，预览账户，导入可读取的地址、类型、显示名和连接设置，完成映射后引导重新授权。仅发现邮箱地址而所有服务器信息都要重填，不能算完整完成“配置导入”，应提供逐字段导入报告。

Outlook Object Model 可以枚举当前 Profile 的账户；更完整的互联网账户配置可能需要 Account Management API / MAPI。不能假定密码或 OAuth token 可被无损迁移。新 Outlook 与经典 Outlook 分开列兼容矩阵，不能复用经典 COM 路径作出承诺。[账户枚举](https://learn.microsoft.com/en-us/office/client-developer/outlook/pia/how-to-get-account-information)、[账户配置属性](https://learn.microsoft.com/en-us/office/client-developer/outlook/auxiliary/properties-account-management-api)、[新 Outlook 扩展差异](https://learn.microsoft.com/en-us/office/dev/add-ins/outlook/one-outlook)

**Win64 与 32 位 Outlook 是额外约束。** 使用 Extended MAPI 时应用须匹配 Outlook 位数。若只交付 x64 组件，则该路线不能覆盖 32 位 Outlook；可另行评估跨进程 OOM、经测试的配置读取或可选 x86 导入桥，但不能默默扩大用户的发布架构范围，也不能把所有 COM 路线都等同于 MAPI 位数限制。[MAPI 位数要求](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/building-mapi-applications-on-32-bit-and-64-bit-platforms)

### 2 PST 内容导入是必做项

建议提供两个可替换导入器：经典 Outlook 可用时走 Outlook/MAPI 适配；脱离 Outlook 时走独立 PST 解析库。必须验证 Unicode/ANSI PST、嵌套文件夹、大文件、附件、嵌入邮件、HTML/纯文本/RTF、时间、已读状态、分类及异常项目。保留原文件，记录每项结果，支持暂停、取消、续传和去重；去重不能仅依赖可能缺失或重复的 Message-ID。

微软发布了 PST 格式规范，但规范存在不代表实现成本低。libpff 可作为候选，项目仍标注 alpha 与 LGPL-3.0-or-later；是否选它取决于实际样本、Windows 构建和分发评估，不在本次直接锁定。商业库也须验证 AOT、许可与数据保真度，不能仅看“支持 .NET”。[PST 规范](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-pst/)、[libpff 项目说明](https://github.com/libyal/libpff)

PST 可包含联系人、日历和任务。首版必做的是邮件与目录；非邮件项目必须在导入报告中可见，若要完整替代 Outlook 的日历等功能则另增范围。OST 是离线缓存，不能直接等同可移植 PST 备份；OST 恢复独立评估。

### 3 规则导入建议做可解释的子集

优先转换常见发件人/收件人/标题条件、例外、移动/复制、标记、分类、优先级与停止后续规则；保留顺序。Outlook 对象模型本身只覆盖规则向导的一部分。脚本、COM 动作、特殊企业条件、不可访问目标和客户端专属行为应列为未转换并默认禁用，不能丢弃条件后开启。[Outlook 规则模型限制](https://learn.microsoft.com/en-us/office/vba/outlook/how-to/rules/managing-rules-in-the-outlook-object-model)

### 4 导出能力

| 格式 | 建议范围 |
| --- | --- |
| EML | 首版必做，单封与批量，尽量保留原始 MIME；文件名冲突和路径安全处理 |
| 本地邮箱归档包 | 首版必做，可恢复邮件、目录及本地元数据；版本化 manifest、校验和、可选加密 |
| MBOX / Maildir | 常用迁移格式，由独立插件提供并标明元数据差异 |
| HTML / 纯文本 / PDF | 面向阅读与分享；不是完整可恢复备份，外部资源仍遵守隐私策略 |
| 附件批量导出 | 目录模板、重名策略、筛选、结果清单 |
| CSV / JSON | 元数据与分析用；不是替代原始邮件 |
| MSG / PST | 后续独立评估库、兼容性和授权成本，不由“能导入”推导“能完整导出” |

账户、规则、任务和插件配置可另行导出模板，默认不含凭据；导入时重新映射账户/目录和缺失插件。

### 5 自定义本地存储

推荐首先实现“目录式工作空间”：SQLite 保存账户、目录、元数据、事务状态与索引；原始 MIME 和大附件使用可校验的对象文件。逻辑上仍是一个本地邮箱，用户通过应用打开，不依赖单一巨型文件。可提供单文件归档包用于搬运与备份；运行时单文件容器是另一存储插件候选，不必首版模拟 PST 内部结构。

数据格式需有版本、原始内容保留策略、校验和、索引重建、崩溃恢复、备份恢复、空间回收和迁移工具。区分“服务器缓存”和“独立本地归档”：删除账户时不能顺便删除归档；清理缓存不能清理唯一副本。SQLite WAL 模式下备份须使用一致性备份机制，不能只复制主数据库文件。

## 五 搜索 规则和定时任务

### 1 共用语义而非三套表达式

建议建立版本化查询 AST 和动作协议。高级搜索字符串、可视化过滤器、收件规则和定时任务的邮件选择器都生成相同条件树；搜索字段、运算符、分词器、内容抽取器、条件和动作均可由插件注册。扩展命名采用命名空间，配置中保存标识、版本和参数，不保存任意 CLR 类型名或任意 SQL。

建议语法示例，仅定义产品意图，待实现语法规范：

```text
account:work folder:inbox (from:example.com OR cc:team@example.com)
received_before:2026-10-01 has:attachment NOT tag:keep
```

搜索覆盖：标题、正文、发件人、实际发送者、Reply-To、To/Cc、可见的 Bcc、附件名称、可选附件全文、收发时间、大小、已读/星标/标签、账户/目录/会话、邮件头、优先级。收件副本通常没有其他人的密送名单，不能承诺搜索不存在的数据。

提供 AND/OR/NOT、分组、精确、短语、前缀、后缀、子串、正则、范围、相对时间、存在/不存在。明确字段类型、大小写、Unicode 归一化、时区、边界是否包含和空值语义。正文未下载、插件缺失、远端查询失败属于未知或不完整，不应自动当作不匹配用于破坏性动作。

本地检索优先，远端搜索按提供者能力补充；显示“仅已同步内容”等覆盖范围。复杂查询先用索引缩小候选，再执行高成本条件。正则有超时和取消，不允许运行于 UI 线程。新增索引字段须安排版本化重建并显示进度。

SQLite FTS5 可作为首版索引候选，但默认 Unicode 分词不是完整中文搜索方案。需评估中文分词或 n-gram 索引；trigram 的全文查询不能覆盖不足三个字符的词，因此“采购”“合同”等两字搜索必须单独验收。[SQLite FTS5](https://www.sqlite.org/fts5.html)

### 2 收件规则

规则包含启用状态、作用账户/目录、触发事件、条件、例外、动作序列、优先级、停止后续规则、执行版本和历史。支持“邮件首次发现”“正文可用”等阶段，但每个阶段及重试不得重复产生副作用。历史导入和初次全量同步默认不当作新收件触发，另提供明确开关。

必须区分本机规则与服务器规则：本机规则在本机执行；服务器规则能力由 provider 单独提供，不能保证语法完全相同。与 Outlook/服务器规则并存时记录谁执行了什么，避免重复移动或转发。

### 3 定时任务的完整模型

```text
调度或事件 → 任务级前置条件 → 目标邮件选择 → 有序动作 → 结果和恢复
```

“邮箱 1 数量超过 1000 封”是前置条件，“邮箱 2 中超过 100 天的邮件”是目标选择，它们可以作用于不同账户。每次运行记录判定时刻、统计范围、选中邮件及动作状态；执行破坏性动作前重新检查邮件是否已被用户修改或移走。

| 维度 | 应支持或预留的内容 |
| --- | --- |
| 时间调度 | 指定时间一次、每 N 分钟/小时/天、固定间隔与完成后间隔、每周多天、每月日期、月末、每月第 N/最后一个星期几、每年、CRON |
| 日历与窗口 | 时区、开始/结束日期、工作日、节假日排除、允许执行时间窗口；节假日数据由插件提供 |
| 事件触发 | 收件、发送完成、同步完成、启动、解锁/恢复、网络恢复、手动、其他任务完成、阈值跨越 |
| 运行策略 | 错过后跳过/补一次/有限补跑、夏令时重复/缺失时间、每月无该日期的处理、并发或互斥、排队/跳过、超时与重试 |
| 任务前置条件 | 账户/目录总数和未读数、消息逻辑大小、服务器配额比例、待同步数、磁盘空间、网络、AC 电源、时段、上次任务成功或失败 |
| 聚合与组合 | AND/OR/NOT、嵌套组、存在/全部/计数/大小合计；统计范围可另带邮件过滤器 |
| 目标选择 | 单/多账户、标签组、目录及子目录、保存搜索、固定快照或每次重新求值；日期、内容、收件人、附件、状态及其组合 |
| 数量限制 | 每次最多 N 封/总字节、按最旧或最大排序、保留最近 N 封、保护标记邮件、处理到低水位 |
| 动作 | 移动、复制、归档、标记已读/未读、星标、分类/标签、提醒、延后提醒、导出、保存附件、生成摘要报告 |
| 高影响动作 | 删除/永久删除、自动回复/转发、外部 webhook 或脚本：独立权限、显式配置及审计；首版可暂不提供任意脚本 |

每种统计必须标明含义，例如“服务器目录逻辑大小”“本地已缓存邮件大小”和“磁盘实际占用”不能混用。远端不能提供配额或尚未同步完整时显示未知；任务按策略等待或跳过，而非将其当 0。阈值触发需迟滞与冷却，例如超过 1000 封启动、清理至 800 封停止，防止每次检查重复触发。

CRON 必须选定并固定方言、时区和星期/日期组合语义，UI 显示未来若干次运行时间。复杂业务条件留在条件树，不塞进 CRON 字符串。后台执行器需持久化任务与状态；只有 GUI 或托盘程序运行时才能执行本机任务。若要求退出 GUI 后继续工作，需单独的用户后台进程；睡眠和关机后的补跑策略需明确。Windows 服务会引入凭据、用户会话和 Outlook 自动化限制，不建议首版默认采用。

### 4 跨邮箱移动是数据可靠性功能

同邮箱移动优先使用 provider 原生能力。跨邮箱/到本地移动采用持久化步骤：读取完整内容 → 写入目标 → 验证内容和必要元数据已持久化 → 记录目标映射 → 删除源 → 记录完成。目标失败不删源；删源失败显示“已复制，源待处理”；重试根据操作 ID 和目标记录去重。崩溃注入测试覆盖每一步，不能承诺分布式严格 exactly-once。

源文件与附件必须全部到位，不能只保存正文摘要就删除服务器副本。目标磁盘不足、目标插件停用、权限变化和远端超时都有可恢复状态。取消应停止后续动作，不应破坏已完成写入；撤销依赖具体 provider，不能虚构普遍可撤销。

也不能假设任意目标都能导入原始收件邮件。Graph 的普通 move API 仅在指定用户邮箱内部移动；跨账户动作需核实目标导入能力与元数据保真度，不支持时明确禁用，而不是用“重新发送给自己”冒充迁移。[Graph move 范围](https://learn.microsoft.com/en-us/graph/api/message-move?view=graph-rest-1.0)

自动回复/转发需循环检测、Auto-Submitted 等消息类型排除、同消息去重、频率上限及因果链；否则规则和多个客户端可能互相触发。

### 5 用户示例的具体表达

```text
名称：工作邮箱旧邮件归档
调度：每天 02:00，Asia/Shanghai；错过后补跑一次
前置：工作邮箱同步结果可用 AND 本地归档位置可写
目标：工作邮箱 → 收件箱 → 接收时间早于本次运行时刻 30 天
排除：星标 OR 标签为“保留”
动作：移动到 本地归档 → 工作邮件 → 按年/月建目录
限制：每次最多 500 封；同一任务不重叠
失败：保留源邮件，记录步骤，可从失败项继续
```

另一个跨账户例子：邮箱 1 收件箱数量超过 1000 封时，处理邮箱 2 收件箱中超过 100 天、标题含“报告”或发件人为指定域、且未标记保留的邮件。UI 应明确展示“触发依据在邮箱 1，实际处理在邮箱 2”，避免误操作。

## 六 收发 编辑与安全查看

### 1 发送与编辑

内置编辑器插件提供纯文本/富文本、To/Cc/Bcc、地址补全、回复/全部回复/转发、引用折叠、附件拖放与内联图片、签名、草稿自动保存、撤销重做、拼写检查扩展、大小提示和发送前检查。联系人与地址建议也是可替换服务；完整通讯录同步与日历不自动纳入首版。

发送身份由账户能力和服务器授权决定，不能任填 From 冒用其他身份。回复默认选原接收账户，有例外时明确显示。切换账户同步调整签名、身份、可用附件限制和草稿归属。处理部分收件人失败、断网、发送后保存已发送副本失败，避免重试造成重复发送。

发件箱持久化，支持排队、取消尚未发送的邮件、定时发送和失败重试。服务器已接受但响应丢失时标记“状态待确认”，先对账再决定重发；不承诺 SMTP 普遍支持幂等。撤销发送通常是发送前延迟，不等同于服务器召回。

### 2 接收与同步

账户增量同步、离线缓存、按目录范围与时间范围同步、附件按需获取、推送或轮询、断线退避、限流、凭据过期和后台状态都由插件协作实现。多账户并发有上限，避免同时启动几十条连接；同一协议连接按库要求串行使用。

同步要处理服务器删除、目录移动/重命名、UIDVALIDITY 改变、token 失效及重建、重复事件和多客户端改动。首次同步先显示头部和最新邮件，后台逐步补全文本，不等待全部内容才允许使用。

### 3 安全阅读

推荐 MIME 解析与 WebView2 渲染分层，阅读器和富文本编辑器分离。Avalonia 官方 WebView 在 Windows 使用 WebView2；选择具体版本后验证 AOT/互操作和请求拦截能力，不能只用一个显示网页的 Demo 验收。[Avalonia WebView](https://docs.avaloniaui.net/docs/app-development/embedding-web-content)

邮件阅读默认禁止脚本、宿主对象、任意 web message、表单提交、弹窗、自动下载和外部导航；HTML 清理、CSP 与网络请求拦截共同生效。外部图片、CSS、字体、音视频、追踪像素和重定向都纳入远程资源策略，不能只过滤 `img`。内嵌 CID 图片通过受控资源映射显示，限制文件类型、大小和解码资源。

允许“仅本封加载”“信任指定发件人/域/规则”等粒度，并可撤销；白名单不能仅因可伪造的显示名称命中。超链接显示目标并由系统浏览器打开，危险协议和本地路径阻止。邮件 WebView 不能共享编辑器或插件页面的高权限桥接接口。[微软 WebView2 安全建议](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security)

编码需要真实样本：UTF-8、GB18030/GBK、Big5、日文编码、错误 charset、RFC 编码标题、嵌套 MIME、TNEF/winmail.dat、RTF、坏 HTML。提供纯文本回退、手动编码与原文查看；对损坏或缺少密钥的受保护邮件给出明确状态，不能承诺任何邮件都无损显示。

S/MIME、PGP、企业 IRM、签名验证、附件预览和反恶意软件检查均保留插件点；是否首版启用取决于需求及兼容测试。保护凭据与加密整个邮件库是两件事：凭据使用系统保护存储；正文、搜索索引、日志、导出和备份的加密策略需一致设计。

## 七 UI 与 UX 建议

⚠️ 功能方向明确，但账户选择、自动化范围及后台状态需要在设计阶段解决。

**H1 状态可见**

- 每个账户可见同步、离线、授权过期、暂停及错误；后台任务有统一入口，不用持续弹窗打断阅读。
- 搜索区显示索引范围、正在查找和可取消状态；切换条件后旧查询结果不能覆盖新结果。

**H2 符合用户理解**

- 主工作区围绕“阅读与处理”“写邮件”“整理自动化”组织。账户和本地归档在同一导航体系内，但区别云端与本地保存。
- 自动化编辑采用“何时运行 → 满足什么条件 → 处理哪些邮件 → 做什么”的顺序，避免直接暴露插件类名和 AST。

**H3 控制与恢复**

- 导入、搜索、归档均可取消或暂停；支持的操作才显示撤销，其他操作显示实际恢复方法。
- 编辑器关闭或插件更换前先保存草稿；失败任务可以只重试失败项。

**H5 预防错误**

- 保存自动化前显示自然语言摘要、目标账户/目录、命中样本、预计数量和副作用；预览不执行写操作。
- 源与目标用文字、图标、路径共同展示，颜色仅作辅助；跨账户与永久删除的影响明确可见。

**H6 识别优于记忆**

- 邮箱/目录选择器支持名称、地址、标签检索，分组、最近使用、多选、目录树和特殊目录；展示能力及不可选原因。
- 用户不必输入 UUID；配置内部仍保存稳定 ID。选择“标签下所有账户”时明确它是动态集合还是当前快照。

**H7 初学者与高级用户兼顾**

- 简单条件构建器与高级搜索语法使用同一语义，能转换的双向同步，复杂扩展不能转换时保留原表达式。
- 支持键盘、批量操作、快捷键、保存搜索、模板；CRON 属于高级入口，常用调度不要求理解表达式。

**H9 错误可恢复**

- 用“授权已过期，重新登录”“目标磁盘空间不足，源邮件已保留”等具体信息；技术日志放展开详情。

优先行动：先完成账户/目录选择器与身份展示；其次验证自动化预览和失败恢复流程；最后用长列表与后台同步同时运行的原型验证心流。参考现有客户端的熟悉概念即可，布局与信息层级应由上述任务决定，不复制其外观。

## 八 性能与可靠性验收

以下数字是建议目标，不是已经测得的结果。基准环境建议 Windows 11 x64、16 GB 内存、SSD、记录具体 CPU；至少测试 10 个账户、1 万与 10 万封邮件，混合中文、HTML、大附件及深目录，另做更大数据压力测试。记录冷/热缓存、索引是否完成、后台同步是否开启。

| 场景 | 初步验收目标 |
| --- | --- |
| 用户点击、输入、修改搜索条件 | 100 ms 内出现反馈；后台任务不能持续占用 UI 线程 |
| 已缓存目录首屏 | 常规条件 p95 不超过 300 ms；只取当前页摘要 |
| 常见本地已索引搜索 | 1 万封首批结果 p95 不超过 1 秒，10 万封目标 2 秒；复杂查询可继续加载 |
| 已缓存普通邮件阅读 | p95 不超过 500 ms；超大邮件单独策略，先给可操作状态 |
| 滚动 | 以 60 Hz 设备流畅为目标，记录丢帧及长帧，不能仅测平均 FPS |
| 取消或替换搜索 | 100 ms 内更新 UI 状态；旧任务可继续退出但不得写回过期结果 |
| 插件重载 | 多轮启停后资源趋于稳定，无残留订阅、文件锁、后台任务；验证在途操作 |
| 迁移与归档 | 任意一步故障后不丢唯一副本，可重新启动恢复；有逐项结果 |

实现原则：UI 虚拟化与数据虚拟化同时做；基于游标/键的分页；摘要和正文分离；后台解析和索引；可取消查询、序号防过期写回；批处理 UI 通知；限制并发与缓存；大附件流式传输；跨进程扩展按批次查询，避免逐封 IPC；全量扫描和复杂正则不能伪装成快速索引查询。

额外可靠性场景：断网、睡眠恢复、token 失效、服务器 429/限流、目录被删除、磁盘满、数据库迁移失败、源邮件已变化、插件崩溃、升级中断、配置半写入、夏令时和时钟跳变。

## 九 NSIS 与 GitHub Release 更新

NSIS 可以安装 win-x64 发布目录；安装器自身位数与被安装应用位数是不同问题。处理 64 位安装路径、注册表视图、快捷方式、协议关联、卸载和用户/全机安装范围即可。[NSIS 官方脚本参考](https://nsis.sourceforge.io/Docs/Chapter4.html)

建议默认每用户安装以减少常规更新权限要求，企业全机安装另设模式。程序、数据、插件和缓存目录分开；卸载默认保留邮箱及归档，数据删除作为明确选项。安装器检测系统 .NET 10 x64，并按实际需要检查 WebView2。

### 发布自动化

发布顺序固定为：使用 generate-changelog 技能生成面向用户的 `changelog.md` 并同步所有发布耦合项目版本 → 提交准备变更 → 创建 `V<version>` Tag → 推送提交和 Tag → GitHub Actions 自动检查、构建、NSIS 打包及创建 Release。`V`/`v` 前缀大小写均接受，项目字段使用不带前缀的版本；不能同时为同一版本发布大小写不同的两个 Tag。

工作流通过 `push.tags` 同时匹配 `V*` 和 `v*`，再校验完整版本；只构建 Tag 指向的提交，版本不一致即失败。Release 正文取该版本 changelog；首次发布只列新功能，后续按实际用户影响区分新增、优化和已发布缺陷修复。所有产物准备完成后才公开 Release，避免更新检查读到缺少安装包的版本。实际 Actions 工作流在建立可构建项目及打包脚本时实现，本次仅记录契约。[GitHub Actions 工作流语法](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)

### 更新组件候选

| 候选 | 已确认的能力 | 对本项目的判断 |
| --- | --- | --- |
| `NetSparkleUpdater.SparkleUpdater` | 更新检查、下载、签名验证、调用安装程序；可自定义 UI，另有 Avalonia UI 包 | 完整更新方案优先验证；保留 NSIS，Actions 额外生成并上传 appcast 和签名 |
| `Octokit` | GitHub API 的 .NET SDK，可获取 Releases 等信息 | 仅需直接读 Release API 时适用；版本/通道筛选、下载验证及安装仍属应用逻辑 |
| `HttpClient` + GitHub Releases API | 不引入额外 SDK，自己实现窄范围检查 | 现成包不适合时的直接后备，不另造更新服务端 |
| Velopack | 成套安装与更新机制 | 自有安装布局及 Update.exe 等约定；不为本次更新检查额外引入第二套安装机制 |

NetSparkle 的主要输入是 appcast，不是任意 GitHub Release JSON。可将 appcast、签名和 NSIS 安装包作为同一 Release 的资产，客户端由配置的仓库发现并固定本次 Release 的资源，仍以 GitHub Releases 为更新源。选择 API 路线时，Octokit 也不等于完整自动更新器。上述属于来源核查，未安装包或验证升级；实现时选择适合 .NET 10 和实际 Avalonia 版本的稳定依赖，不直接依赖开发分支 API。[NetSparkle 官方说明](https://github.com/NetSparkleUpdater/NetSparkle)、[NetSparkle NuGet](https://www.nuget.org/packages/NetSparkleUpdater.SparkleUpdater/)、[Octokit 官方说明](https://github.com/octokit/octokit.net)、[Velopack 安装约定](https://docs.velopack.io/packaging/installer)

仓库地址在实施自动更新时从 Git remote 与配置确认，若届时仍缺少 GitHub owner/repo 再提醒用户；当前不要求提供，也不填写假地址。现阶段优先验证 NetSparkle，最终是否采用完整框架或仅使用 Octokit/HttpClient 取决于实际检查和安装需求。

GitHub Releases 可以提供版本及下载资产，但不是完整更新系统。建议内置更新源插件负责读取发布信息，固定的更新执行组件负责验证、退出应用与替换文件：

1. 明确 stable/prerelease 通道、版本比较、CPU 架构、最低系统与运行时要求。
2. 拉取版本化清单，包含版本、下载地址、大小、哈希、插件 SDK 范围和数据库兼容范围；清单及程序有可信签名验证。
3. 支持代理、超时、断点/重试和缓存；公开仓库无需把私人 token 嵌入客户端，私有仓库另行授权。
4. 下载后校验，暂停新任务、保存草稿并排空关键操作；退出后由独立 updater 或经验证的 NSIS 升级流程替换。
5. 新版本启动检查通过后确认升级。数据库升级采用可恢复迁移；二进制回滚不意味着新数据库一定能被旧版读取。

GitHub 的 release assets API 提供 digest 等元数据，可用于一致性检查，但与发布文件放在同一受控来源的哈希不能单独证明发布者身份。签名、公钥/证书信任和降级策略需要在更新方案中明确。[GitHub Release assets API](https://docs.github.com/en/rest/releases/assets)

应用更新和插件更新分开处理；核心插件更新下次启动生效，普通插件更新遵循卸载协议。首版使用全量更新即可，差分更新后置。GitHub 在目标网络不可达时要能查看原因和手动安装，不自动换到未配置的镜像。

## 十 分阶段范围和决策门槛

### 阶段 0 技术与产品验证

- 验证已选 JIT 框架依赖的实际发布，包含列表、MIME、SQLite、HTML 查看与编辑；记录启动、占用、包大小和系统 .NET 检测结果。
- 重点验证 CordiSharp 外部插件依赖、UI 贡献、配置重载、循环卸载和资源释放；不再安排 NativeAOT、C ABI 或 WASM 插件路线的选型试验。
- 用户公司 Exchange 的登录、列目录、同步、正文/附件、发送、已读、移动和失败恢复必须真实通过；确认本地/云部署及认证策略。
- 经典 Outlook 账户信息与连接配置导入、32/64 位边界；独立 PST 解析与实际样本保真。
- 跨邮箱到本地归档的中断恢复；中文两字词搜索；阅读器远程资源零默认请求。

不能用 Debug 运行通过充当框架依赖安装包验收，也不能用个人 Outlook.com 成功充当公司 Exchange 成功。验证前复用本地 SDK、依赖、安装包和邮件样本；不反复下载资源。GUI 验证前完成构建和数据准备，集中一次完成证据采集，完成后结束测试进程。

### 阶段 1 邮件工作流闭环

插件宿主及双配置、账户模型、QQ/163/通用 IMAP + SMTP、POP3、Outlook.com、已验证的公司 Exchange、本地邮箱、增量同步、离线阅读、编辑发送、基础搜索、安全渲染、账户配置导入和 PST 导入、EML/归档导出。

这阶段可以有中间测试版，但在公司 Exchange、账户配置和 PST 导入缺失时，不应宣称原始必做需求已完成。

### 阶段 2 自动化与完整交互

统一条件树、收件规则、调度与阈值、跨邮箱可靠移动、预览、重试和审计；完善高级搜索、标签与选择器；覆盖 10 万封性能测试。规则导入先做可解释子集。

### 阶段 3 发布与外部扩展

NSIS、系统依赖检查、Tag 触发的 GitHub Actions 自动发布、GitHub 更新、备份恢复、外部插件 SDK/样例/兼容测试；完成声明中所有插件点的替换验证。附件全文、更多导出格式、加密邮件、复杂企业能力按实际需要增加，不默认全部塞入首版。

### 规模判断

这属于完整邮件客户端工程，主要成本在协议差异、同步状态、迁移保真、富文本安全及可靠自动化，不能按普通 CRUD 桌面应用估算。粗略规划可给阶段 0 约 2–4 个日历周，由熟悉 .NET 桌面与邮件协议的小团队进行；生产可用首版应按数月而非数周安排。具体人月和上线日期要在公司 Exchange、PST 库、UI 插件形式及已选 JIT 部署链路通过验证后估算，当前不提供虚假的精确承诺。

仍需冻结的事项：公司 Exchange 与 Outlook 版本/位数；外部插件是否要求任意原生 Avalonia 控件；GUI 退出后的后台执行要求；商业依赖预算；本地格式必须单文件还是允许目录式；联系人/日历、受保护邮件与共享邮箱的首版范围。更新组件的最终版本及仓库地址在对应功能实施时确认。

## 十一 已确认决定

用户已确认 **Avalonia + C# + .NET 10，全 JIT、框架依赖发布，系统 .NET 由用户安装；CordiSharp 优先复用，插件契约和生命周期由本项目适配层约束；NSIS 安装，GitHub Releases 更新**。

发布由 generate-changelog 准备记录与版本后打 Tag 并推送，GitHub Actions 自动构建和发布；规范以根目录 `AGENTS.md` 为执行入口。自动更新优先复用合适 NuGet 包，现有候选为 NetSparkle 与 Octokit，均不适合时直接对接 GitHub API。NativeAOT 相关内容仅作为此前选型依据保留。
